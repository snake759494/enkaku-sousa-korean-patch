# 타이틀·시스템 메뉴 추적 기록

v2.2부터 릴리즈 노트에 이렇게 적어 왔습니다.

> 타이틀 메뉴는 찾지 못했습니다. USRDIR 전 파일(0012 404MB 포함)에 텍스처
> 스트림이 없고, 실행 파일에도 Shift-JIS/UTF-8/UTF-16 어느 형태로도 문자열이
> 없으며, 스크립트에도 없습니다.

**이 진술은 두 군데가 틀렸습니다.** 아래에 무엇이 틀렸고 무엇이 실제로 확인됐는지 적습니다.

## 1. 실행 파일에 문자열이 있습니다

없던 게 아니라 **찾는 형태가 틀렸습니다.**

이 게임은 대사를 Shift-JIS로 저장하지 않습니다. 히라가나는 0x28부터 1바이트, 한자는 0x88~0x8D 선두의 2바이트로 폰트 슬롯을 가리킵니다. 메뉴가 같은 폰트로 그려진다면 저장 방식도 같을 텐데, Shift-JIS만 훑었으니 나올 리가 없었습니다.

게임 인코딩으로 찾으니 `BOOT.BIN`에서 바로 나왔습니다. `BOOT.BIN`은 암호화되지 않은 평문 ELF입니다(엔트로피 6.39, `EBOOT.BIN`은 8.00).

```
0x103700 부근   시스템 메시지
0x103000 부근   증거품 설명
0x107c00~0x115000  인물 메모, 증언, 사건 자료
```

해독한 예:

```
セーブされていませんがよろしいですか？
メモリスティックにセーブします。
すでにインストールデータが存在します。
上書きしてよろしいですか？
メモリースティックの空き容量が不足しています。
```

## 2. 가나표에 글자가 5개 빠져 있었습니다

처음 해독하니 「メモリスティックばセーブぜゃぞ。」처럼 가나가 어긋났습니다. 스크립트 해독기의 가나표가 `あ`부터 시작하는데, **게임 표에는 앞에 작은 모음 `ぁぃぅぇぉ`가 더 있습니다.** 넣으니 「ろをぜえぬぞぐ？」가 「よろしいですか？」로 정확히 풀립니다.

## 3. 한자는 아직 못 풉니다 — 그리고 왜 못 푸는지

`88 F5 88 F6` 두 글자가 `存在`여야 합니다(「インストールデータが存在します」). 그런데 **스크립트 폰트의 245·246번 글리프는 `妻`·`赤`입니다.** 짐작이 아니라 그려서 확인했습니다. `存`은 183번, `在`는 143번에 있습니다.

같은 선두 바이트에서 trail이 1 늘었는데 슬롯이 40 뒤로 뛰므로, **계산식이 아니라 대응표**입니다. 그래서 대응표를 찾았고, 없었습니다.

| 가설 | 검증 방법 | 결과 |
|---|---|---|
| 인덱스 → Shift-JIS 표 | Shift-JIS 한자 코드가 100개 이상 연속하는 구간 검색 | 0건 |
| 인덱스 → 폰트 슬롯 표 | 245→183, 246→143, 154→170, 334→190 을 동시에 만족하는 표 검색 (u8/u16/LE/BE) | 0건 |
| 바이트쌍 → 슬롯 표 | 183·143이 인접한 위치를 찾고 나머지 세 예측으로 검증 | 0건 |
| 두 번째 글리프 아틀라스 | 4bpp 글리프 형태 점수로 전 파일 스캔 후 육안 확인 | 후보 전부 코드·데이터 |
| 폰트가 1368자보다 길다 | 원본 stream1을 글리프 1368번 이후까지 렌더링 | 잡음 (폰트는 1368에서 끝남) |

## 4. 아카이브 0001~0004에도 스트림이 있습니다

이전 스캔이 **0x800 정렬만** 봤습니다. 0000이 거기에 스트림을 두기 때문인데, 이 파일들은 **0x800 + 0x40** 위치에 둡니다. 모든 탐침이 헤더에서 64바이트씩 빗나갔고, 그래서 "텍스처 스트림 없음"이 나왔습니다.

정렬을 고치니:

```
0001    276 스트림
0002    568 스트림
0003    126 스트림
0004      9 스트림
0011      0 스트림
```

압축을 풀면 stream0과 같은 모양의 u32 오프셋 표가 나옵니다. 다만 **헤더 배치가 다릅니다.** stream0은 record 0의 첫 워드가 크기표 위치인데, 이쪽은 거기가 0이고 0x40 위치에 (표 오프셋, 개수)가 들어 있습니다. 그 값으로 읽으면 아직 말이 되는 가로·세로가 나오지 않아, 컨테이너 해독은 미완입니다.

## 5. 글꼴은 공유됩니다 — 다만 시스템 메시지만 다릅니다 (추가 조사)

"메뉴가 다른 글꼴을 쓴다"는 위의 결론은 **절반만 맞았습니다.**

스크립트가 쓰는 글꼴 슬롯으로 이름을 인코딩해 `BOOT.BIN`에서 찾아보니 **그대로 나옵니다.**

| 낱말 | 슬롯 | 바이트 | BOOT.BIN |
|---|---|---|---|
| `沼崎` | 37, 38 | `88 25 88 26` | 0x101d50 |
| `佳代` | 243, 244 | `88 f3 88 f4` | 0x102aae |
| `白川` | 21, 22 | `88 15 88 16` | 0x101ce3 |
| `斉藤` | 105, 106 | `88 69 88 6a` | 0x101e9c |

네 개가 우연히 맞을 확률은 없습니다. 그 구역(`0x101c00`~`0x102c00`)을 해독하면 `水谷`·`のぞみ`·`アリバイ`·`タクシー`·`リモコン`·`プレイヤー`·`被疑者`처럼 이 게임의 낱말이 제대로 읽힙니다. **같은 글꼴, 같은 공식입니다.**

그런데 시스템 메시지 구역(`0x1037xx`)만 어긋납니다. `セーブ` 다음에 오는 `89 48 89 49`는 슬롯 325·326인데, 그 글리프를 그려 보면 **`駅`·`便`**입니다. 화면에는 `削除`가 나옵니다. `[245][246]`도 `存在` 자리인데 글리프는 `妻`·`赤`입니다.

`0x11fd7d` 부근에는 `セーブフラグ`·`スクリプトムービー`·`ゲームオーバー時のセーブフラグ` 같은 **개발용 변수 이름**이 같은 방식으로 들어 있고, 역시 한자가 어긋납니다.

그리고 `セーブ`(바이트 `BE B0 83 75` — 반각 가나와 Shift-JIS를 섞어 씁니다)는 **ISO 전체에서 `BOOT.BIN`의 그 구역에만** 있습니다. 아카이브에도, 압축 스트림 안에도 사본이 없습니다.

즉 시스템 문자열이 가리키는 글꼴은 따로 있고, 그것은

- `USRDIR/0000` 안에 없고 (텍스처 449장 전수 확인)
- `stream1` 안의 두 번째 아틀라스도 아니며 (글리프 형태 점수로 전 구간 훑음 — 폰트는 1368자에서 끝남)
- `BOOT.BIN` 안의 4bpp 글리프도 아닙니다 (상위 후보 세 곳을 그려 보니 전부 MIPS 코드)

## 6. 역어셈블로 글꼴을 찾았습니다 (해결)

`BOOT.BIN`은 평문 MIPS ELF입니다. 파일 `0x54`가 가상 주소 `0x8804000`에 실리므로 `가상주소 = 파일오프셋 + 0x8803FAC`입니다.

**세이브 메뉴를 그리는 코드**를 먼저 찾았습니다. `0x88814cc`:

```
lw    $t0, 0x7590($v0)      ; 문자열 포인터[0] = セーブ
addiu $a0, $zero, 0xd4      ; x = 212
addiu $a1, $zero, 0x74      ; y = 116
jal   0x884cf1c             ; 그리기
...
lw    $t0, 0x7594($v0)      ; 포인터[1] = 削除
addiu $a1, $zero, 0x86      ; y = 134
```

**문자 해독기**는 `0x884be84`입니다. 첫머리가 핵심이었습니다.

```
lw    $v1, [0x8a02c14]
slt   $v1, $a0, $v1         ; 문자열이 그보다 앞이면
bnez  → $a3 = 0x88EA760     ;   실행 파일 안의 글꼴
else  → $a3 = [0x89f5e18]   ;   stream1 의 글꼴
sw    $a3, [0x8a02c38]
```

**글꼴이 둘입니다.** 대사는 stream1 것을 쓰고, 실행 파일 안의 문자열은 실행 파일 안의 것을 씁니다. "메뉴가 대사 글꼴을 이상하게 가리킨다"고 본 것이 처음부터 틀렸습니다 — 애초에 다른 글꼴이었습니다.

인코딩도 확정됐습니다.

```
1바이트 0x28..0x7A   Shift-JIS 히라가나, code = 0x8200 | (b + 0x77)
1바이트 0xA7..0xDD   반각 가타카나, 0x88EA394 의 표로 Shift-JIS 변환
2바이트 선두 0x81..0x9F, 0xE0..0xFC   code = (lead << 8) | trail
code <  0x8800       0x8890F10 글꼴 (가나·기호)
code >= 0x8800       index = ((code - 0x8800) >> 8) * 253 + (code & 0xFF)
                     glyph = base + (index >> 1) * 256
```

즉 **가나는 평범한 Shift-JIS**이고, 한자는 Shift-JIS가 비워 둔 `0x8800`부터를 사유 영역으로 쓴 것입니다.

`253`이 상수 검색에 안 걸린 이유도 밝혀졌습니다. 컴파일러가 `((x << 6) - x) << 2) + x`로 풀어 놓았습니다(`0x884c03c`).

**검증**했습니다. 이 글꼴에서

```
325·326 = 削除    245·246 = 存在    154·334 = 上書    0·1 = 黙秘
```

예측이 전부 맞습니다. 문자열도 온전히 읽힙니다 — `削除`, `黙秘：`, `人物：`, `場所：`, `証拠：`, `１１月`, `の調査予定`, `【調査場所】`, `を入手`, `午前と午後の予定は`, `調査を終了しますか？`.

글꼴은 파일 `0xe67b4`부터 세그먼트 끝까지, **1952 글리프**입니다. 완전히 빈 타일은 **2개(4 글리프)**뿐입니다.

**타이틀 메뉴 문자열은 실행 파일에 없습니다.** `から`(바이트 `32 70`) 71곳을 전부 해독했지만 `最初から`·`続きから`는 없습니다. 그것은 아직 다른 곳입니다.

## 남은 장벽: 실행 파일은 암호화되어 배포됩니다

`BOOT.BIN`은 평문이지만 **PSP가 실제로 싣는 것은 `EBOOT.BIN`**이고, 그쪽은 `~PSP` 암호화본입니다(엔트로피 8.00). `BOOT.BIN`을 고쳐도 게임에 반영되지 않습니다.

한글로 바꾸려면 실행 파일을 고쳐야 하고, 그러려면

- `EBOOT.BIN` 자리에 평문 ELF를 넣어야 합니다 (CFW·PPSSPP는 받아들이지만 정품 펌웨어는 아닙니다), 그리고
- 글리프 자리가 4개뿐이므로, 메뉴가 쓰지 않는 한자 슬롯을 찾아 한글로 덮어써야 하며,
- 문자열은 제자리에서 길이를 늘릴 수 없습니다. `セーブ`(5바이트)를 `저장`(4+NUL=5)으로, `削除`(5바이트)를 `삭제`(5)로 바꾸는 것은 정확히 들어맞습니다.

이 프로젝트는 실기 구동을 지키려고 ISO를 제자리에서만 고쳐 왔습니다(v1.1의 `C1-2858-3`). 실행 파일 교체는 그 조건을 깨므로, 진행 여부는 판단이 필요합니다.

## 다음에 볼 곳

1. **0001~0004 컨테이너 헤더 확정.** 스트림은 열리고 팔레트(1024바이트)도 보이므로 남은 것은 크기표 배치뿐입니다. 가장 유망합니다.
2. **BOOT.BIN 역어셈블.** 메뉴를 그리는 함수가 글리프를 어디서 읽는지 따라가면 한자 출처가 나옵니다. 확실하지만 비쌉니다.
3. 한글 패치는 **한자 출처를 찾은 뒤**에야 가능합니다. 한글 글리프는 stream1 폰트에 넣어 두었는데, 메뉴가 그 폰트를 쓰지 않는다면 닿지 않습니다.
